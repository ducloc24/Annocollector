# Annocollector

Monorepo with a FastAPI backend (Supabase Postgres + Alembic) and a Next.js
frontend.

```
.
├── .env                 # Supabase credentials (git-ignored, shared by be)
├── be/                  # FastAPI + SQLAlchemy async + Alembic
│   ├── app/
│   │   ├── api/         # HTTP layer (v1 endpoints)
│   │   ├── core/        # config, logging, exceptions
│   │   ├── db/          # engine, session, declarative base
│   │   ├── models/      # SQLAlchemy models
│   │   ├── schemas/     # Pydantic schemas
│   │   ├── repositories/# data access
│   │   └── services/    # business logic
│   ├── alembic/         # migrations
│   └── tests/
├── fe/                  # Next.js 16 (App Router) + TypeScript + Tailwind v4
│   └── src/
│       ├── app/
│       ├── components/
│       └── lib/api.ts   # typed API client
├── docker-compose.yml
└── package.json         # root scripts
```

## Quick start

Requirements: Python 3.11+, [uv](https://docs.astral.sh/uv/), Node.js 20+,
a Supabase project.

```bash
npm install                 # root tooling (concurrently)
npm run setup               # fe deps + be deps (uv, creates be/.venv)

copy .env.example .env      # then fill SUPABASE_PASSWORD (real password)
copy fe\.env.example fe\.env.local

npm run db:migrate          # apply Alembic migrations to Supabase
npm run dev                 # backend :8000 + frontend :3000
```

- Frontend: http://localhost:3000
- API docs: http://localhost:8000/docs
- Health: http://localhost:8000/api/v1/health

## One-command launcher

`scripts/start.ps1` does the whole bring-up and streams both logs to the same
terminal:

1. reads the root `.env` and runs a real `SELECT 1` against Supabase (asyncpg);
2. checks ports 8000/3000 and reports which process is blocking them;
3. installs backend deps with `uv sync` if `be/.venv` is missing/incomplete;
4. applies `alembic upgrade head`;
5. installs frontend deps with `npm install` if `fe/node_modules` is missing;
6. starts uvicorn + Next.js and prints a summary with both URLs.

```bash
npm run start
# or
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start.ps1
```

Useful flags:

| Flag            | Effect                                              |
| --------------- | --------------------------------------------------- |
| `-CheckOnly`    | Only check DB + ports, then exit                    |
| `-SkipDbCheck`  | Skip the database check                             |
| `-SkipMigrate`  | Do not run Alembic                                  |
| `-SkipInstall`  | Fail instead of installing missing dependencies     |
| `-Force`        | Kill whatever is holding port 8000/3000             |
| `-BePort 8001`  | Run the API on another port                         |

The `-ExecutionPolicy Bypass` part is needed on machines where running `.ps1`
files is disabled (that is why the npm script includes it).

## Database

The repo-root `.env` holds the Supabase connection parts. The backend composes
the connection string at runtime (no credentials in code):

```
SUPABASE_HOST=aws-0-eu-west-1.pooler.supabase.com
SUPABASE_PORT=6543                  # transaction pooler (app)
SUPABASE_MIGRATION_PORT=5432        # session pooler (migrations/DDL)
SUPABASE_DB=postgres
SUPABASE_USER=postgres.<project-ref>
SUPABASE_PASSWORD=<your-database-password>
```

- The app connects through the **transaction pooler** with `NullPool` and
  prepared-statement caching disabled (required by Supavisor).
- Alembic connects through the **session pooler** for DDL.
- You can bypass all of it with an explicit `DATABASE_URL` /
  `MIGRATION_DATABASE_URL`.
- Without Supabase settings the backend falls back to a local SQLite file, so
  the test suite and a fresh clone still work.

### Migrations (Alembic)

```bash
npm run db:migrate                    # alembic upgrade head
npm run db:revision -- "add notes"    # autogenerate a new migration
```

Or from `be/`:

```bash
uv run alembic revision --autogenerate -m "add notes"
uv run alembic upgrade head
uv run alembic downgrade -1
uv run alembic current
```

Always review autogenerated migrations before applying them. Alembic records
applied versions in the `alembic_version` table; SQLAlchemy models never create
tables outside the test suite (`AUTO_CREATE_TABLES=false`).

## Scripts

| Command             | What it does                                      |
| ------------------- | ------------------------------------------------- |
| `npm run start`     | Full launcher: DB check → ports → be + fe (logs live) |
| `npm run setup`     | Install frontend + backend dependencies           |
| `npm run dev`       | Run API and web app together                      |
| `npm run dev:be`    | Migrate + API only (uvicorn, reload, :8000)       |
| `npm run dev:fe`    | Web app only (Next.js, :3000)                     |
| `npm run build`     | Production build of the frontend                  |
| `npm run lint`      | Ruff (backend) + ESLint (frontend)                |
| `npm run format`    | Ruff formatter                                    |
| `npm run test`      | Pytest (backend, SQLite)                          |
| `npm run typecheck` | mypy (backend) + tsc (frontend)                   |
| `npm run db:migrate` | `alembic upgrade head`                            |
| `npm run db:revision` | `alembic revision --autogenerate -m <message>`   |

## Docker

```bash
docker compose up --build
```

The API container reads the root `.env`, runs `alembic upgrade head` and then
starts uvicorn. The frontend is built with `NEXT_PUBLIC_API_URL` pointing at
`http://localhost:8000/api/v1`.

## Backend layout in one line

`endpoint → service → repository → database`: endpoints only handle HTTP,
services hold business rules, repositories only query, schemas define the
contract. Errors are normalized to `{code, message, details}`.
